## 1. 目标与边界

### 1.1 目标

把「单管理员博客」演进为「博客 + 小型社区」：**访客可注册成为作者，投稿文章，经管理员审核后发布，并拥有个人主页**。原有博客功能（浏览/评论/点赞/RSS 等）不受影响。

### 1.2 本期边界（做什么 / 不做什么）

| 做 | 不做（后续迭代） |
| --- | --- |
| 注册 / 登录 / 登出 / 注销账号 | 邮箱验证码与找回密码（邮件服务） |
| 投稿（Markdown 编辑器前台复用）、草稿、编辑、删除 | 第三方登录（GitHub/微信） |
| 管理员审核（通过 / 退回 + 退回原因） | 用户互相关注与私信 |
| 个人主页（`/user/:id`，展示已发布文章与资料） | 用户等级/积分/徽章 |
| 后台用户管理（列表、封禁/解封）、投稿审核页 | 多管理员协作审核 |
| 登录身份评论（昵称自动带入，游客评论保留） | 评论 only-logged-in 强制（见 §11 决策点 2） |

> 明确不做 SSR 迁移：社区化在现有 SPA 架构内完成。

## 2. 形态决策：投稿审核制

| 维度 | 方案 A：投稿审核制（**推荐**） | 方案 B：直接发布制 |
| --- | --- | --- |
| 内容质量 | 管理员把关，垃圾/广告内容进不来 | 完全依赖事后治理 |
| 与现有结构契合 | 复用 article.status 流转（新增待审核态即可） | 需要引入"作者自治发布"语义，个人博客定位被稀释 |
| 管理成本 | 每篇投稿需人工审核 | 零审核成本 |
| 适合阶段 | 社区初期（注册用户少、质量优先） | 成熟开放社区 |

**结论**：采用方案 A。审核通过后文章 `user_id` 保持投稿者，署名清晰；管理员拥有一切管理权。

## 3. 角色与权限矩阵

角色沿用 `user.role`（`ADMIN` / `USER`，v1 设计预留），访客不注册。

| 功能 | 访客 | USER（注册用户） | ADMIN |
| --- | :-: | :-: | :-: |
| 浏览 / 搜索 / RSS | ✓ | ✓ | ✓ |
| 游客评论（昵称+内容） | ✓ | ✓ | ✓ |
| 注册 / 登录 | — | ✓ | ✓ |
| 登录身份评论（user_id 关联） | — | ✓ | ✓ |
| 投稿（写文章、存草稿、提交审核） | — | ✓ | ✓ |
| 编辑 / 删除**自己的**草稿与被退回稿 | — | ✓ | — |
| 删除自己已发布文章 | — | ✗（申请管理员下架） | ✓ |
| 审核（通过 / 退回） | — | — | ✓ |
| 后台全部管理功能 | — | — | ✓ |
| 用户管理（封禁 / 解封） | — | — | ✓ |
| 个人主页查看 | ✓（看任何人） | ✓ | ✓ |

关键原则：

1. **`/api/admin/**` 加角色硬校验**（`@SaCheckRole("ADMIN")` 或路由级 `StpUtil.checkRole`）——这是本次最重要的安全变更，注册用户的 token 必须被管理端拒绝；
2. **资源归属校验在 Service 层**：投稿编辑/删除接口校验 `article.user_id == 当前登录 id`，杜绝越权改他人文章；
3. 封禁用户（status=0）：登录被拒、存量 token 踢出（Sa-Token `logout`）、其文章与评论仍在（可由管理员决定隐藏）。

## 4. 表结构变更（影响面刻意收窄）

### 4.1 `article`（2 处）

| 变更 | 说明 |
| --- | --- |
| `status` 枚举扩展 | 现有 0 草稿 / 1 已发布 / 2 已下架 基础上新增 **3 待审核**、**4 已退回** |
| 新增 `reject_reason VARCHAR(255)` | 退回原因（USER 端可见），通过/发布时置空 |

`user_id` 语义自然扩展为"作者"——现有文章 `user_id=1`（管理员）无需任何迁移。

### 4.2 `user`（1 处）

| 变更 | 说明 |
| --- | --- |
| `email` 加唯一约束（可空） | 注册邮箱占用防重复；NULL 不参与唯一性 |

> 不新增密码重置、邮箱验证等字段（本期边界外）。

### 4.3 `comment`（0 处，激活预留字段）

`user_id` 已预留：登录用户评论写入 `user_id`，`nickname` 自动取用户昵称（不可篡改）；游客评论逻辑不变。

### 4.4 不新增任何表

投稿、审核、个人主页全部由现有表 + 新状态承载。**总表数维持 10 张。**

## 5. API 设计

### 5.1 新增：前台认证组 `/api/front/auth`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /register | 注册 `{username, password, nickname, email?}`；用户名唯一、密码 6~32、注册限频（Redis，同 IP 每小时 5 次） |
| POST | /login | 统一登录（ADMIN/USER 共用）→ `{token, role, 用户信息}`；封禁账号拒绝 |
| POST | /logout | 注销 |
| GET | /profile | 当前登录用户信息 |
| PUT | /profile | 修改昵称 / 头像 / 邮箱 / 简介 |

### 5.2 新增：投稿组 `/api/front/my/articles`（均需登录）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | / | 我的文章分页（含各状态数量统计） |
| POST | / | 投稿/存草稿 `{title, summary?, coverImage?, categoryId?, tagIds[], content, action: draft\|submit}` |
| PUT | /{id} | 编辑（仅本人，且状态 ∈ 草稿/已退回；重新提交审核） |
| DELETE | /{id} | 删除（仅本人，且状态 ≠ 已发布） |
| GET | /{id} | 详情（本人，编辑回显；被退回时含 reject_reason） |

### 5.3 新增：个人主页 `/api/front/user/{id}`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /user/{id} | 用户公开资料 + 其已发布文章分页 |
| GET | /user/{id}/comments | 该用户的评论（可选，本期一并做） |

### 5.4 后台新增 `/api/admin` 组

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /review/page | 投稿审核分页（status=3/4 筛选） |
| PUT | /review/{id}/approve | 通过 → status=1 |
| PUT | /review/{id}/reject | 退回 `{reason}` → status=4 |
| GET | /users/page | 用户分页（关键词/状态筛选，含投稿数） |
| PUT | /users/{id}/status | 封禁 / 解封（禁封 ADMIN） |
| PUT | /users/{id}/reset-password | 管理员重置密码（生成随机密码返回一次） |

> 现有 `/api/admin/**` 全部追加 ADMIN 角色校验（见 §3）。

## 8. 安全设计

1. **密码**：BCrypt 存储（现有）；注册密码强度 6~32 位；
2. **注册限频**：Redis 同 IP 每小时 5 次（复用 RateLimitUtil，新 scene）；
3. **越权防护**：投稿编辑/删除在 Service 层校验归属；`/api/admin/**` 角色校验后端强制；
4. **XSS**：投稿 Markdown 走前台既有 sanitizeHtml 管线；评论昵称锁定为账号昵称；
5. **封禁即踢**：封禁调用 `StpUtil.logout(userId)` 立即失效存量会话；
6. **信息泄露**：/user/{id} 仅返回昵称/头像/简介/文章，不返回邮箱等敏感字段。

## 9. 兼容与迁移

- **零数据迁移**：现有表字段完全够用（`user.role`、`article.user_id/status`、`comment.user_id` 均为 v1 预留）；仅 `article` 加 1 列、`user.email` 加唯一键；
- 已发布文章、RSS、sitemap、站点配置、MinIO 图床均不受影响；
- 前台游客态行为不变（不强制注册）。

## 11. 决策点（已拍板）

| # | 决策点 | 选项 | 结论 |
| --- | --- | --- | --- |
| 1 | 投稿模式 | A 审核制 / B 直接发布 | **A**（§2） |
| 2 | 评论身份 | A 游客+登录双轨 / B 仅登录可评论 | **B**（评审决定：仅登录可评论，留言板同步此政策） |
| 3 | 注册邮箱 | A 选填不验证 / B 必填+邮件验证 | **A**（邮件服务列后续迭代） |
| 4 | 用户删除已发布文章 | A 不可自删，申请管理员 / B 可自删（逻辑删除） | **A**（保护已发布内容与外链） |
