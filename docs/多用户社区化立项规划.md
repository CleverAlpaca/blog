# 多用户社区化 · 立项规划

| 项 | 内容 |
| --- | --- |
| 版本 | v1.0 |
| 日期 | 2026-10-31 |
| 状态 | 待评审（评审通过后按里程碑 M1→M4 实施） |
| 前置 | 基于《设计文档》v1.3+ 的单用户博客（当前 10 张表，附录 B 迭代已落地至 v1.5） |
| 已确认决策 | 注册方式一期采用**用户名+密码**；投稿采用**审核制**；一期为**完整范围** |

---

## 1. 背景与目标

### 1.1 现状

- 单管理员博客：仅一名 ADMIN 写作，访客免登录浏览、评论（昵称+邮箱）、点赞
- `user` 表建表时已预留 `role`（ADMIN/USER）、`status`（启用/禁用）字段
- `article.user_id`、`comment.user_id`、`message.user_id`、`like_record.visitor_id` 均已预留归属字段

### 1.2 一期目标

1. 访客可注册成为 USER（用户名+密码），登录后评论/点赞归属自己
2. 注册用户可**投稿**：写作（Markdown）→ 提交审核 → 管理员通过后公开展示
3. 每个用户拥有**个人主页**（`/user/{id}`）与**用户中心**（资料/我的文章/我的评论）
4. 管理员获得**审核队列**与**用户管理**能力

### 1.3 非目标（二期及以后）

邮箱验证码注册、GitHub OAuth 登录、积分/等级、用户间私信、投稿邮件通知、敏感词自动过滤。

## 2. 角色与权限矩阵

| 角色 | 能力 |
| --- | --- |
| 游客 | 浏览、游客评论（昵称+邮箱，现状不变）、点赞（设备标识） |
| USER（注册用户） | 游客全部能力 + 登录态评论（归属自己、免填昵称）、投稿（草稿/提交审核）、用户中心、个人主页 |
| ADMIN | 现有后台全部能力 + 审核队列（通过/驳回）+ 用户管理（禁用/启用）+ 查看所有用户文章 |

**接口维度**（Sa-Token 拦截规则）：

| 前缀 | 要求 | 说明 |
| --- | --- | --- |
| `/api/front/**` | 匿名放行 | 现状不变 |
| `/api/user/**` | 登录即可（USER 或 ADMIN） | 一期新增：注册(匿名)/登录(匿名)/投稿/用户中心 |
| `/api/admin/**` | 登录 **且 ADMIN 角色** | **安全加固点**：现仅校验登录，任何登录用户可访问，本立项必须补 `@SaCheckRole("ADMIN")` |

## 3. 功能范围（一期）

### 3.1 前台新增/改造

| 模块 | 功能 |
| --- | --- |
| 注册/登录 | `/register`、`/login`：用户名（3~20 字符，唯一）+ 密码（6~32 位，BCrypt）+ 昵称（注册时设置，可选头像）；登录失败锁定提示复用现有异常体系 |
| 登录态评论/留言 | 登录后评论框免填昵称，`user_id` 落库、展示头像；游客通道保留 |
| 投稿 | `/write`：复用 md-editor-v3 编辑器；保存草稿 / 提交审核；「我的文章」可见四态流转（草稿→待审核→已发布/已驳回+驳回理由），可编辑再提交 |
| 个人主页 | `/user/{id}`：头像/昵称/简介 + 该用户已发布文章列表（复用 ArticleList 组件）；从文章作者名点击进入 |
| 用户中心 | `/me`：资料修改（昵称/头像上传/简介/密码修改，复用图床）、我的文章、我的评论 |
| 页头 | 登录入口按钮；登录后显示头像下拉（用户中心/我的主页/退出） |

### 3.2 后台新增/改造

| 模块 | 功能 |
| --- | --- |
| 审核队列 | 待审核列表 → 查看 → 通过（status→1 已发布，作者可见）/ 驳回（填驳回理由，status→4，作者可见理由） |
| 用户管理 | 用户列表（昵称/角色/状态/注册时间/文章数）、禁用/启用（禁用后立即踢下线且无法登录） |
| 文章管理改造 | 列表增加「作者」列；可见所有用户文章；下架/删除权限不变 |

## 4. 数据库变更设计

**原则：最大化复用建表时预留的字段，零新表，仅一处 ALTER。**

### 4.1 user 表 —— 零变更

`role`（ADMIN/USER）、`status`、`username`（唯一）、`password`（BCrypt）、`nickname`、`avatar`、`intro`、`email` 全部满足一期需求。

### 4.2 article 表 —— 仅一处 ALTER（2 个变更）

| 变更 | 内容 | 说明 |
| --- | --- | --- |
| status 枚举扩展 | 0 草稿 / 1 已发布 / 2 已下架 / **3 待审核 / 4 已驳回** | TINYINT 容量足够，语义向后兼容 |
| 新增字段 | `reject_reason VARCHAR(255) DEFAULT ''`（驳回理由） | 驳回时填写，作者在「我的文章」可见 |

现有 3 篇文章的 `user_id` 保持归属 admin，无需数据迁移。FULLTEXT 索引不受影响（新增/修改内容自动进索引）。

### 4.3 其余表 —— 零变更

`comment/message.user_id`（登录归属）、`like_record.visitor_id`（登录后存 `user:{id}` 形式）、`site_config` 均无需改动。

### 4.4 状态流转图（投稿文章）

```
用户：草稿(0) ──提交审核──▶ 待审核(3) ──管理员通过──▶ 已发布(1)
  ▲                          │                          
  └──── 编辑再提交 ◀── 驳回(4) ◀── 管理员驳回（填理由）
已发布(1) 仍可被管理员下架(2)/删除；作者编辑已发布文章 → 回到待审核(3)
```

## 5. 接口设计（新增，前缀规则遵循现有体系）

### 5.1 用户认证 `/api/user/auth`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | /register | 注册：`{ username, password, nickname }`（匿名可访问） |
| POST | /login | 登录 → `{ token, 用户信息 }`（与后台 token 同体系） |
| POST | /logout | 退出 |

### 5.2 用户中心 `/api/user`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /profile | 我的资料 |
| PUT | /profile | 修改资料/密码 |
| GET | /articles | 我的文章分页（四态筛选） |
| POST | /articles | 新建草稿/提交审核 |
| PUT | /articles/{id} | 编辑（校验归属：仅本人） |
| DELETE | /articles/{id} | 删除（仅草稿/已驳回可删） |
| GET | /comments | 我的评论分页 |

### 5.3 后台审核与管理 `/api/admin`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | /review/list | 待审核分页 |
| PUT | /review/{id}/approve | 通过（→已发布） |
| PUT | /review/{id}/reject | 驳回（body: `{ reason }` → 已驳回） |
| GET | /users | 用户分页 |
| PUT | /users/{id}/status | 禁用/启用（禁用即 StpUtil.logout 踢下线） |

### 5.4 可见性控制（关键点）

`GET /api/front/article/{id}` 对 status=3/4 的文章：**仅作者本人与 ADMIN 可见**（依据登录态与 user_id 判定），其余访客返回 404——待审核内容不可泄露。

## 6. 鉴权方案（Sa-Token）

1. **单一账号体系**：USER 与 ADMIN 共用 `StpUtil`（一期不做多账号隔离），登录后 token 通用
2. **角色数据**：新增 `StpInterfaceImpl` 实现 `getRoleList(userId)` → 读 `user.role`（ADMIN/USER），供 `@SaCheckRole` 生效
3. **后台加固**：`/api/admin/**` 在现有登录校验之上追加 `@SaCheckRole("ADMIN")`（或拦截器内统一 `StpUtil.checkRole("ADMIN")`）——**安全修复随本立项落地**
4. **禁用语义**：`user.status=0` 登录拒绝；管理端禁用操作同步 `StpUtil.logout(userId)` 踢下线

## 8. 里程碑与预估

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| M1 鉴权与账号 | 注册/登录/退出、StpInterface 角色加固、前台登录态、游客/登录评论并存 | 注册即登录；游客评论不变；USER 无法访问 /api/admin/**（403）；后台登录不受影响 |
| M2 投稿与审核 | /write、我的文章四态流转、审核队列（通过/驳回）、可见性控制、后台文章管理作者列 | 用户投稿 → 管理员通过 → 前台可见且作者可点；驳回理由作者可见；未登录访客看不到待审核文章 |
| M3 个人主页与用户中心 | /user/{id}、/me 三 Tab、资料修改、登录评论头像归属 | 主页展示该用户已发布文章；资料/密码修改生效 |
| M4 用户管理与收尾 | 用户禁用/启用、文档同步、全量回归 | 禁用用户被踢下线且无法登录；全部既有功能回归通过 |

预估总工作量：**约为「暗黑模式 + RSS」轮的 1.5~2 倍**（涉及鉴权改造与 5 个新页面）。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| `/api/admin/**` 角色漏洞（现状任何登录用户可进后台） | M1 强制加固，作为验收第一标准 |
| 垃圾投稿 | 审核制天然兜底；提交频率复用 RateLimitUtil 限流 |
| 游客评论与登录评论并存的数据一致性 | `comment.user_id` 与 `nickname` 双写并存：登录用户昵称取自用户表且前端锁定昵称输入 |
| 搜索/看板/热门榜单被用户文章影响 | 均基于 status=1 查询，自动包含审核通过的用户投稿（预期行为）；看板增加「待审核数」卡片 |
| token 未区分端（前台登录 token 可访问后台接口） | M1 角色加固后 USER 访问后台接口一律 403，风险闭环 |
| 二期依赖 | 邮箱验证/OAuth 需要外部服务，二期立项时单独评估 |

## 10. 决策记录

| 决策点 | 结论 | 依据 |
| --- | --- | --- |
| 注册方式 | 一期用户名+密码；邮箱验证/GitHub OAuth 二期 | 一期不引入 SMTP/OAuth 外部依赖 |
| 投稿机制 | 审核制 | 个人博客内容质量可控 |
| 一期范围 | 完整范围（注册/投稿/审核/主页/用户中心） | 一次形成闭环 |
| 数据库策略 | 复用预留字段，仅 article 一处 ALTER，零新表 | 建表时已预留，成本最低 |
